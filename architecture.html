t2ai
architecture

An AI fitness coach built as a hybrid system: deterministic code owns state, safety, and adaptation; AI owns extraction, explanation, and summarization. The cleanest mental model is state → deterministic decision → AI explanation → user action.

Five layers

Reading top to bottom is the request path. Each layer has a single responsibility and a narrow contract with the layer above and below.

Two flows that define the product

Everything else is a variation of these. Reading them end-to-end shows exactly where the LLM is trusted and where it isn't.

Flow A

Daily coaching

User opens the dashboard. We recommend today's workout, adapted to how they feel, with a short explanation.

  1. UIFetch state from /api/profile and /api/readiness.
  2. APILoad profile, plan, latest readiness from Postgres.
  3. DecisionassessReadiness() → green / yellow / red.
  4. DecisionAdjust volume + intensity based on level.
  5. RetrievalPull relevant cues + memory from pgvector (deterministic ranker if RAG is off).
  6. AIAsk LLM for a concise coach message (Zod-typed).
  7. APIValidate output → safety gate → return to UI.
  8. UIRender plan + explanation + confidence badge.
Flow B

Form analysis

User uploads a squat video. The browser extracts pose, deterministic code scores the reps, and the LLM translates numbers into cues.

  1. UIUpload lift video into the squat analyzer.
  2. VisionMediaPipe Pose Landmarker runs in-browser → landmarks per frame.
  3. UIPOST landmarks (not the video) to /api/squat/analyze.
  4. DecisionCompute rep metrics: depth, heel lift, knee tracking, tempo.
  5. DecisionScore each rep into good / needs work / poor. Source of truth.
  6. AILLM summarizes structured metrics into 2–3 cues (Zod-typed).
  7. DBPersist metrics + cues to squat_runs; feeds back as a low-weight note in next plan generation.

Why · What · When · How · Where

The design decisions behind the diagram, in one screen.

What

A hybrid AI product

t2ai is an AI fitness coach that plans your workouts, adapts them to how you feel, and (next) grades your form from video.

The system is intentionally not a chatbot wrapper. LLMs do what they're good at — parsing messy language, drafting, summarizing. Rules do everything safety-critical.

Why

Rules decide, AI explains

Handing a model full control over volume, intensity, or injury avoidance is how AI products earn their reputation for being confidently wrong.

Every LLM call in this repo goes through timeout → Zod → deterministic safety gate → persist. Model output is untrusted until it passes those checks.

When

Five milestones

M1 — Done: persistence, today dashboard, readiness check-in, safe swap, Ollama coaching.

M2 — Done: 35 Promptfoo eval cases across 6 datasets, fixture provider routing.

M3 — Done: pgvector knowledge chunks, Ollama embeddings, retrieval-grounded explanations.

M4 — Done: Browser-side MediaPipe, deterministic squat scoring, LLM coaching cues, adaptation hook.

M5 — In progress: README polish, architecture refresh, demo script, eval/cost notes.

How

Control plane + data plane

The Next.js app is the control plane: auth, validation, orchestration, persistence. It never leaks model URLs to the browser.

The data plane is swappable: fixture for tests, ollama on a private Mac mini for dev, gemini for hosted demos. Cloud is never a silent fallback.

Where

Runs here today

Web: Vercel (planned) · Next.js 16 App Router · React 19 · Tailwind v4.

Backend: Next.js route handlers in src/app/api/* · Zod at every boundary.

Data: Supabase Postgres (migrations in supabase/migrations) with in-memory fallback for local dev without a key.

AI: Vercel AI SDK · Ollama on localhost or *.local (public URLs are refused in src/lib/ai.ts).

Trade-off

What this buys you

The layered boundary is the whole point. You can swap the model, the database, or the retrieval store one at a time without touching the others.

It costs more plumbing up front than a "call the API and render" chatbot — and pays it back the first time a model hallucinates a swap you can't actually do.
